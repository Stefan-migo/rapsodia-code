# ODD Tasks — update-integrity

**Branch:** `odd/update-integrity` · **Worktree:** `../rapsodia-code-odd-update-integrity`
**Base:** `origin/main` @ `6e74744` (v1.0.1, released 2026-09-20)
**TDD:** OFF — this repository has no test harness (`npm test` exits 1: "No test files found").
Functional checks only; no RED/GREEN cycle is claimed. Runner: none.

## Objective

Make `rapso update` leave a project **correct and converged**: the bytes it writes must be the
bytes it hashed, and one update must be enough.

## Problem

`v1.0.1` shipped native Windows support. The `init` path is sound — a project generated by
`rapsodia-code@1.0.1` on Windows is correct (41 files, no placeholders left, `python` resolved
instead of the Store-alias `python3`). The **`update` path is not**, and it is the path every
existing user takes.

All of this was reproduced by executing the published artifact on Windows, not by reading code.
Harness: the published `dist/index.js` run from PowerShell with the real machine+user `PATH`,
in `%TEMP%\opencode\rapso-test` (1.0.1) and `%TEMP%\opencode\rapso-up` (1.0.0, for the upgrade).

### D1 — `update` writes raw template bytes (the core defect)

`cli/src/commands/update.ts` reads `readFileSync(templatePath)` and writes it straight to the
project at three sites (`:170-171` modified, `:186-187` user-modified overwrite, `:211-212`
added). It never imports or calls `substituteVariables`.

`detectChanges` classifies with `hashTemplateFile` — which hashes the **substituted** bytes
(`template.ts:115-118`). So classify and write disagree by construction.

Reproduced: a project created by `1.0.0`, updated with the `1.0.1` CLI:

```
opencode.json:48  "command": ["{PYTHON_COMMAND}", "-m", "graphify.serve", "graphify-out/graph.json"]
AGENTS.md:150     This is the **{PROJECT_NAME}** project, created on {DATE}.
USER-GUIDE.md:10  cd {PROJECT_NAME}
wiki/log.md:9     ## [{DATE}] init | {PROJECT_NAME} Wiki Created
scripts/setup.sh:3  # {PROJECT_NAME} — Project Setup
```

The Graphify MCP server is left dead. This re-breaks, through the upgrade path, exactly the
defect `v1.0.1` advertises as fixed.

`template.ts:45-54` states the invariant the author already knew:

> `copyTemplate` and `hashTemplateFile` both route through this function, so the hash recorded for
> the generated file is the hash of the bytes that were actually written; resolving it anywhere
> else would make every project report `opencode.json` as modified forever.

`update` is that "anywhere else".

### D2 — the project never converges

Consequence of D1, plus its own cause below. After applying an update, a follow-up
`update --check` still reports `10 file(s) have auto-updates pending`.

### D2b — `update` clobbers `createdAt` (independent)

`update.ts:248` rewrites `createdAt: new Date().toISOString().split('T')[0]` on every run.
`detectChanges` derives the substitution variables from `manifest.createdAt`
(`manifest.ts:81-86`: `date: manifest.createdAt`, `year: createdAt.slice(0,4)`). So updating a
project on any day other than its creation date shifts the substitution date, and every
`{DATE}`/`{YEAR}`-bearing template file (`AGENTS.md`, `wiki/log.md`) is rewritten on every
future update while the project's recorded creation date drifts to the last update.

Not visible in the reproduction above only because that project was created the same day.

### D3 — a legacy Windows manifest is never repaired (silent)

`manifest.ts:72` keys the map with the **raw** manifest path, and `:112` compares the raw
manifest path against `templateSet`. `collectFiles` already normalizes to `/`
(`template.ts:73`), so a manifest written by a pre-1.0.1 Windows CLI — which stored
backslashes — matches nothing.

Reproduced: a `1.0.0`-created project on Windows holds 34 entries of the form
`".opencode\\agents\\rapso-developer.md"`. The `1.0.1` update classified exactly those 34 as
declining from the template and re-added them, and `update.ts:226/229/237` compares raw paths
too, so the stale backslash entries are never replaced — the manifest grows duplicates
(`Files tracked: 41` → `73`).

`cli/src/commands/adopt.ts:131` has the same shape (`oldHashes` keyed by raw `file.path`,
probed at `:142` with a normalized path), so a legacy manifest makes adopt misclassify too.

There is no shared manifest loader: `update.ts:87`, `adopt.ts:127` and `project.ts:72` each
parse their own.

### D4 — `templateVersion` is a hardcoded lie

`'1.0.0'` is written at `manifest.ts:32`, `update.ts:247` and `adopt.ts:~207`, while
`cli/package.json` is `1.0.1`. A project created by 1.0.1 reports `Template: 1.0.0` in `status`
and in `update --check`. Verified live.

`templateVersion` is **display/metadata only** — no control flow branches on it (the `--check`
gate at `update.ts:96-110` and the no-op gate at `:114-117` branch on
`added`/`modified`/`userModified` lengths). Safe to correct.

### D5 — a fresh project always reports 2 phantom removals

Verified empirically against the published template: the manifest holds 41 paths, the template
39, and the difference is exactly `.gitignore` and `.opencode/.gitignore`.

`init` writes both itself (`init.ts` → `writeProjectIgnores`), and `generateManifest` walks the
whole target directory (`manifest.ts:25-29`, filtering only `.rapsodia-code/` and `.git/`), so
they enter the manifest. They cannot exist in the template because npm never publishes a file
named `.gitignore`. `manifest.ts:112` therefore reports them as removed from every project,
forever — which is what makes a real removal impossible to spot.

The v1.0.1 release notes contradict themselves here: _Highlights_ claim #52 ended the phantom
removals, while _Known gaps_ still lists them. Live, a fresh 1.0.1 project still prints
`2 file(s) removed from template`.

## Scope

Authorized — `cli/src/**` only:

- `cli/src/engine/template.ts` — export the substitution projector
- `cli/src/engine/manifest.ts` — options helper, path normalization, ignore-file exclusion, version
- `cli/src/commands/update.ts` — substitute on write, preserve `createdAt`, normalize paths, version
- `cli/src/commands/adopt.ts` — normalize paths on read, version
- `odd/tasks/update-integrity.md` — this document

## Tasks

Each task closes with `npm run typecheck` + `npm run build` from `cli/`, and one atomic commit.
`cli/dist/` is gitignored and is never committed.

**W1 — write the bytes you hashed (D1).**
`template.ts`: export a projector that mirrors `copyTemplate`'s text/binary rule
(`isTextFile` → `substituteVariables`, else raw bytes). `manifest.ts`: export the
`TemplateOptions` reconstruction currently inline at `:81-86` and call it from `detectChanges`.
`update.ts`: build those options once and replace the three raw read/write sites with the
projector. The options **must** be the same object `detectChanges` uses, or the files carrying
`{DATE}`/`{YEAR}` stay stale forever.
Check: superseded by W6's end-to-end scenario.

**W2 — stop clobbering `createdAt` (D2b).**
`update.ts:248`: preserve `manifest.createdAt`. Do not introduce a separate "updatedAt" field —
`createdAt` is the substitution source and must keep meaning "the date this project was created".
Check: superseded by W6.

**W3 — normalize manifest paths on read (D3).**
A single exported normalizer, applied where a manifest is read (`update.ts`, `adopt.ts`) so a
legacy backslash manifest is repaired on the next write instead of being duplicated.

**W4 — exclude the CLI's own ignore files from the manifest (D5).**
`manifest.ts:29`: exclude `.gitignore` and `.opencode/.gitignore` alongside the existing
`.rapsodia-code/` and `.git/` filters. Must compare normalized, since the walk yields OS
separators before `:27`. Do **not** route this through `excludedPaths` — that filter is applied
to the template file list (`:57`), not to the deleted loop (`:112`).

**W5 — source `templateVersion` from the real version (D4).**
Replace the three `'1.0.0'` literals with the CLI's own version. A working reader already exists
at `utils/defect.ts:80` (`join(__dirname, '..', 'package.json')`), which resolves after bundling
because `__dirname` is `cli/dist`. Hoist one shared constant rather than three copies.
`index.ts:19` and `utils/mcp.ts:103` carry the same hardcoded string — worth folding in if it
stays one small edit, otherwise record it.

**W6 — end-to-end acceptance on Windows (the honest check).**
The repository has no test harness, so the verification is the scenario that found this:

1. `npm i rapsodia-code@1.0.0` in a scratch dir; `rapso init legacy --yes --no-git`.
2. Run the **built worktree** CLI: `rapso update --force`.
3. Assert `grep -rnE '\{(PROJECT_NAME|DATE|YEAR|PYTHON_COMMAND)\}' legacy` returns **nothing**.
4. Assert `rapso update --check` reports the template up to date and **0** files removed.
5. Assert the manifest holds no backslash paths and no duplicate entries.
6. Assert a fresh `rapso init` project reports `Template: <the built version>`, not `1.0.0`.

A backslash manifest for step 5 is produced by creating the legacy project with the 1.0.0 CLI on
Windows, which is exactly what the published tarball does.

## Risks

- The `TemplateOptions` object must be shared between classify and write; two reconstructions that
  drift apart is the failure mode this whole change exists to remove.
- Normalizing paths on read mutates what is later persisted. That is intended (it migrates the
  manifest), and `/` is canonical on every platform, but it must not be applied to `excludedPaths`
  patterns, which are glob-ish and already normalized at their own comparison site (`:58-62`).
- `adopt.ts` is touched for D3/D4 only. Do not refactor it.
